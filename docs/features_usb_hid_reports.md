# USB HID 리포트 구성과 동시 입력 (V260823R1)

## 1. 목적과 범위
- 이 펌웨어가 호스트에 무엇을 어떤 모양으로 보고하는지, 그리고 동시 입력 한계가 어디서 오는지를 기록한다.
- 코드 구조는 지식그래프로 질의한다(AGENTS.md §3). 이 문서에 두는 것은 **코드만 봐서는 복원되지 않는 것** — 부트 규격과의 편차, 그 편차를 유지하기로 한 근거, NKRO를 도입하지 않기로 한 근거다.
- 대상: `src/hw/driver/usb/usb_hid/usbd_hid.{c,h}`(디스크립터·엔드포인트), `src/hw/driver/usb/usb_cmp/usbd_cmp.c`(Composite 모드의 같은 구성), `src/ap/modules/qmk/port/protocol/host.c`(전송 진입점).

## 2. 인터페이스 구성

| 인터페이스 | 엔드포인트 | wMaxPacketSize | subclass / protocol | 내용 |
| --- | --- | --- | --- | --- |
| 0 | `0x81` IN | 64B | 1 (BOOT) / 1 (Keyboard) | 키보드. **20키 배열, IN 22바이트** |
| 1 | `0x84` IN / `0x04` OUT | 32B | 0 / 0 | VIA raw HID |
| 2 (EXK) | `0x85` IN | 8B | 1 / 0 | SYSTEM(ID 3, 3B) / CONSUMER(ID 4, 3B) / **MOUSE(ID 2, 6B)** |

- `bInterval`은 세 인터페이스 모두 `usbBootModeGetHsInterval()`을 따르므로 선택한 폴링 레이트가 그대로 적용된다.
- MOUSE는 V260823R1에 EXK 인터페이스에 추가됐다. 리포트가 6바이트라 **기존 8바이트 엔드포인트에 그대로 들어가므로 엔드포인트 크기와 FIFO 배분은 변경되지 않았다.**
- 디스크립터가 선언한 크기와 QMK 구조체 크기는 `usbd_hid.c`의 `_Static_assert` 3개로 컴파일 시점에 고정한다(MOUSE 6B이고 EP 크기 이하 / EXTRA 3B).
- Composite(CDC+HID) 모드의 `usbd_cmp.c`는 같은 상수(`HID_EXK_EP_SIZE`, `HID_EXK_REPORT_DESC_SIZE`)에서 디스크립터를 조립하므로 두 모드가 자동으로 일치한다.

## 3. 동시 입력은 20키다 (6KRO가 아니다)
`HW_KEYS_PRESS_MAX`가 20이다(`src/hw/hw_caps_keys.h:15`, 5개 보드 모두 override 없음). 따라서 인터페이스 0의 IN 리포트는 mods(1) + reserved(1) + keys[**20**] = **22바이트**다. 빌드된 이미지에서 추출한 디스크립터가 `... 95 14 75 08 ...`(REPORT_COUNT = 0x14 = 20)로 이를 확증한다.

- 리포트 디스크립터를 파싱하는 호스트(모든 현대 OS)는 **20키 동시 입력**을 그대로 인식한다.
- 21번째 키는 `add_key_byte()`(`port/protocol/report.c`)에서 빈 슬롯을 찾지 못해 **조용히 무시된다**. ErrorRollOver(0x01)를 보내지 않는다. 실사용에서 도달할 수 없는 한계다.

## 4. 부트 규격과의 편차 (알려진 상태, 유지 결정)

| | 이 펌웨어 (인터페이스 0) | HID Boot Keyboard 규격 |
| --- | --- | --- |
| IN 리포트 | 22바이트 — mods(1) + reserved(1) + keys[20] | 8바이트 — mods(1) + reserved(1) + keys[6] |
| OUT 리포트 | 1바이트 (LED 5비트 + 패딩 3) | 동일 |
| 인터페이스 선언 | subclass 1(BOOT), protocol 1(Keyboard) | 동일 |

**BIOS에서 동작해 온 이유**: 22바이트의 **앞 8바이트가 부트 포맷과 바이트 단위로 정확히 같다**(mods, reserved, keys[0..5]). 8바이트만 읽는 호스트는 부트 키보드가 보낸 것과 동일한 데이터를 받으므로 앞 6키가 정확히 동작한다.

**규격 편차 두 가지**:
1. `SET_PROTOCOL(boot)`을 받아도 리포트를 8바이트로 줄이지 않는다. `usbHidSendReport()`는 인자 `length`와 무관하게 항상 `HID_KEYBOARD_REPORT_SIZE`(22)를 전송한다. HID 1.11 §7.2.6은 boot protocol에서 8바이트를 요구한다.
2. 인터페이스 0의 `GET_REPORT`(0x01)에 핸들러가 없어 STALL된다. 인터럽트 IN 대신 컨트롤 전송으로 폴링하는 호스트가 있다면 실패한다.

**남는 위험은 내용이 아니라 전송 크기다.** 호스트가 8바이트짜리 TD로 IN을 걸면 22바이트 응답은 babble이 되어 엔드포인트가 halt될 수 있다. 다만 EFI USB HID 드라이버를 포함한 대부분의 호스트 스택은 `wMaxPacketSize`(64)로 버퍼를 잡으므로 통과한다.

**결정(오너, 2026-08-23)**: 두 편차 모두 **고치지 않고 유지**한다. 출시된 이미지가 이 동작으로 현장에서 쓰이고 있고 실패 보고가 없으며, 고치려면 재시도 큐와 SOF 드레인이 얽힌 8000Hz 송신 경로를 프로토콜 상태에 따라 가변 길이로 바꿔야 한다. 특정 BIOS/KVM에서 실패가 보고되면 그때 ①(boot일 때 8바이트 절단)부터 검토한다.

**따라서 "BIOS 호환"은 규격상 보장이 아니라 앞 8바이트 일치에 기댄 실무적 호환이다.** 이 구분을 문서·릴리스 노트에서 흐리지 않는다.

## 5. NKRO를 도입하지 않는 이유 (2026-08-23 평가 결과)
V260823R1 작업 중 NKRO(240키, 별도 리포트 ID)를 구현해 보고 **되돌렸다.** 근거:

- **기능적 실익이 없다.** 기본 상태가 이미 전환 없이 20키다. 20 → 240은 사람이 도달할 수 없는 구간이고, 풀사이즈 104키 보드에서도 의미가 없다.
- **비용이 전 사용자에게 부과된다.** NKRO 리포트는 32바이트라 EXK 엔드포인트를 8B → 32B로 키워야 하고(= 모든 사용자 재열거), 재시도 큐 RAM이 1152B → 4224B로 는다. NKRO를 켜지 않는 사용자도 이 비용을 진다.
- **전환 자체가 사라진다.** 6KRO↔NKRO 토글은 "부트 호환이냐 동시입력이냐"의 교환을 사용자에게 떠넘기는 장치다. 현재 구성은 앞 8바이트로 부트 호환을 유지하면서 20키를 함께 주므로 교환할 것이 없다.
- 되돌린 구현은 이 커밋 이전 이력에 남아 있다. 다시 필요해지면 EXK 인터페이스에 리포트 ID 6을 추가하고 `keyboard_protocol`을 `SET_PROTOCOL` `wIndex==0`에 연결하는 방식이 그대로 유효하다.

**V260823R1 이전에도 NKRO 토글은 제공된 적이 없다.** `NKRO_ENABLE`이 정의된 적이 없어(`git log -S "NKRO_ENABLE" -- src/ap/modules/qmk/CMakeLists.txt`가 빔) `keymap_config.nkro` 비트는 아무 효과가 없었다. 즉 이 결정은 현상 유지이며 회귀가 아니다.

| --- | --- |
| BIOS/UEFI에서 키가 안 먹는다 | USB POLLING을 1 kHz (FS)로 낮춰 본다. 그래도 안 되면 §4의 두 편차를 의심한다. |
| OS에서 20키를 넘겨도 더 안 들어간다 | 정상이다. §3의 배열 크기 한계다. |
