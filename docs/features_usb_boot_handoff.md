# 부트로더 → 펌웨어 인계 시 USB 재열거 (V260824R2)

관련 코드: `src/hw/driver/usb/usbd_conf.c` 의 `USBD_LL_Start()`
관련 저장소: [eerraa-qmk-h7s-boot](https://github.com/eerraa/eerraa-qmk-h7s-boot) — `docs/uf2_auto_start.md`, 커밋 `19e0487`

---

## 1. 왜 펌웨어에 지연 코드가 들어갔는가

### 증상

UF2 부트로더에 펌웨어를 업로드하면 업로드 자체는 항상 성공하는데,
**부트로더에서 펌웨어로 자동 전환되는 동작이 간헐적으로 실패**했다.
무반응 상태에서 USB 케이블을 재삽입하면 업로드한 펌웨어가 정상 부팅됐다.
재현 조건을 특정할 수 없었다.

### 원인 (부트로더 측)

부트로더 `bootJumpFirm()`은 시스템 리셋이 아니라 **직접 점프**로 펌웨어를 시작한다.
그 직전의 `usbDeInit()`은 RCC 클럭 게이팅만 수행했다.

```c
// 부트로더 (수정 전)
void usbDeInit(void)
{
  __HAL_RCC_USB_OTG_HS_CLK_DISABLE();   // 클럭만 차단
  __HAL_RCC_USBPHYC_CLK_DISABLE();
  HAL_NVIC_DisableIRQ(OTG_HS_IRQn);
}
```

클럭 게이팅은 주변장치 레지스터를 리셋하지 않는다. 따라서 `DCTL.SDIS`는 0으로 남아
**PHY의 D+ 풀업 / HS 터미네이션이 그대로 유지된다.** 호스트 입장에서 장치는 분리된 것이
아니라 *붙어 있는데 응답만 안 하는* 상태다. 그 상태로 펌웨어가 올라오면 호스트는
예전 MSC 장치를 계속 상대하고, OTG 코어 소프트리셋으로 장치 주소가 0이 된 펌웨어는
영원히 열거되지 않는다.

### 왜 펌웨어가 이를 보완할 수 있는가

USB의 분리/부착은 부트로더와 펌웨어 사이의 소프트웨어 인수인계가 아니라
**D+/D- 선의 전기적 상태**이고, 그 상태는 `USB_OTG_HS->DCTL`의 **SDIS 비트 하나**가
결정한다. USB 주변장치는 부트로더 전용도 펌웨어 전용도 아닌 **같은 칩의 같은 주변장치**이며,
점프 이후에는 CPU도 그 레지스터도 전부 펌웨어 소유다.

즉 "≥100ms짜리 분리 신호를 아무도 내지 않았다"가 문제이므로,
**그다음에 CPU를 쥔 쪽(=펌웨어)이 내면 된다.**

### 핵심: 펌웨어는 이미 분리 신호를 내고 있었다

`usbBegin()` 내부에서 실제로 벌어지는 일이다.

| 호출 | 하는 일 |
|---|---|
| `USBD_Init()` → `HAL_PCD_Init()` 끝 | `USB_DevDisconnect()` → **SDIS = 1 (분리)** |
| ↓ FIFO 설정 + `USBD_RegisterClass()` | **수백 µs** |
| `USBD_Start()` → `HAL_PCD_Start()` | `USB_DevConnect()` → **SDIS = 0 (부착)** |

분리 구간이 수백 µs에 불과해 호스트/허브 디바운스(100ms)에 못 미쳤을 뿐이다.
따라서 보완책은 **새로운 동작을 추가하는 것이 아니라, 이미 존재하는 분리 구간의 유지
시간을 100ms로 늘리는 것**이다.

```c
USBD_StatusTypeDef USBD_LL_Start(USBD_HandleTypeDef *pdev)
{
  delay(USBD_BOOT_DETACH_HOLD_MS);        // HAL_PCD_Init 이 세워둔 SDIS 를 100ms 유지
  hal_status = HAL_PCD_Start(pdev->pData);
  ...
```

### 타임라인

```
[정상 — 케이블 재삽입]
  분리 ████████████████████ 부착 → 디바운스 → 버스리셋 → 열거 → HID 인식  OK

[보완 전 — 부트로더 점프]
  부트로더 usbDeInit(): 클럭만 차단 → 풀업 그대로 = 호스트 눈엔 "여전히 붙어있음"
  ───────────────────────────────────────────  (150~400ms 무응답)
  펌웨어 HAL_PCD_Init:  ▍           ← SDIS=1 이지만 수백 us
  펌웨어 HAL_PCD_Start: 부착
  호스트: 못 봄 → 예전 MSC 장치로 계속 취급 → 새 HID 열거 안 함 → 무반응  FAIL

[보완 후]
  펌웨어 HAL_PCD_Init:  ████████████ ← SDIS=1 을 100ms 유지
  펌웨어 HAL_PCD_Start: 부착
  호스트: 분리 인식 → MSC 스택 해제 → 재열거 → HID 인식  OK
```

### 왜 간헐적이었는가

부트로더에는 원인이 하나 더 있다. `uf2_flash_complete()`가 `tud_task()` 안에서
`bootUpdateFirm()`을 직접 수행해 외장 플래시 소거·복사 동안 **1.5~5초간 USB 스택이
정지**한다(W25Q16JV 64KB 블록 소거 6회, typ 150ms / max 2000ms per 블록).

그 정지 구간에서 호스트가 SCSI 타임아웃으로 MSC 스택을 **먼저 내려버리면** 이후
펌웨어의 재접속이 "새 장치 부착"으로 보여 성공하고, 호스트가 참고 기다렸으면 실패했다.
소거 시간 편차와 호스트 컨트롤러 차이 때문에 사실상 무작위였다.

### 근거가 된 비대칭

| 경로 | USB 상태 | 결과 |
|---|---|---|
| 전원 인가(콜드부트) → 펌웨어 | 부트로더 `bootUp()`이 `usbInit()`보다 **먼저** 실행 → USB를 켠 적 없음 | 항상 정상 |
| 케이블 재삽입 | 전원 사이클 = PHY 리셋 | 항상 정상 |
| 펌웨어 → 부트로더 | 펌웨어가 `HAL_NVIC_SystemReset()` 사용 (+100ms 디태치) | 항상 정상 |
| **부트로더 → 펌웨어 (UF2 직후)** | **점프. 디태치 없음.** | **간헐 실패** |

정상 동작하는 세 경로는 전부 "USB가 붙은 적이 없거나, 하드웨어 리셋으로 PHY가
초기화된" 경우다. 실패하는 경로만 유일하게 살아있는 USB 세션을 물려받았다.

## 2. 같은 기법의 선례

이 프로젝트는 이미 동일한 논리를 쓰고 있다. VIA에서 리셋을 요청할 때의 경로다
(`src/hw/driver/usb/usb.c` 의 `usbProcessDeferredReset()`).

```c
USBD_Stop(&USBD_Device);
USBD_DeInit(&USBD_Device);
delay(USB_RESET_DETACH_DELAY_MS);   // V251109R7: 호스트가 디태치를 감지할 시간을 제공
resetToReset();
```

`USB_RESET_DETACH_DELAY_MS`(100ms)라는 상수도 이미 정의되어 있다.
본 변경은 검증된 기법을 **부팅 경로에도 적용**한 것이다.
두 상수를 공유하지 않고 `usbd_conf.c`에 `USBD_BOOT_DETACH_HOLD_MS`를 따로 둔 것은,
전자는 "리셋 전 디태치 유예", 후자는 "부팅 시 디태치 유지"로 목적이 달라 각각
독립적으로 조정 가능해야 하기 때문이다.

## 3. 적용 위치를 `USBD_LL_Start()`로 고른 이유

- `USBD_Start()`는 `usbBegin()`의 4개 모드 분기(CDC/MSC/HID/CMP)에서 각각 호출된다.
  `USBD_LL_Start()` 한 곳에 두면 모든 모드가 자동으로 커버된다.
- `HAL_PCD_Init()`이 이미 SDIS=1로 끝내 놓은 직후 지점이므로, 별도로 SDIS를 조작할
  필요 없이 지연만으로 유효한 디태치 구간이 만들어진다.
- `usbBegin()`은 `hwInit()`에서 부팅 시 1회만 호출된다. 재진입·주기 실행 경로가 없어
  블로킹 지연이 안전하다.

### 조건부 적용을 하지 않은 이유

"점프로 들어온 경우에만" 지연하도록 판별하는 것도 가능하다. 부트로더는 USB 주변장치를
리셋하지 않으므로 `DCFG.DAD`(호스트가 배정한 장치 주소)가 0이 아니면 살아있는 USB
세션을 물려받았다는 뜻이고, 콜드부트에서는 0이다(부트로더 `bootUp()`이 `usbInit()`보다
먼저 실행되어 USB를 켠 적이 없다).

그러나 `HAL_PCD_Init()`이 **MspInit(클럭 인가) → `USB_CoreReset`(DAD를 0으로 리셋)**을
한 호출 안에서 처리하므로, DAD를 읽으려면 그 전에 RCC 클럭을 직접 켜는 중복 초기화가
필요하다. 100ms를 아끼려고 하드웨어 의존적인 판별 코드를 넣을 이유가 없어
**무조건 적용**으로 정했다. 부팅 시간 증가는 100ms이며, 부트로더의 펌웨어 검증·SRAM
복사에 이미 수백 ms가 소요되는 점을 감안하면 무시 가능하다.

## 4. 이 보완책의 한계

§1의 "왜 간헐적이었는가"에서 설명한 **USB 스택 정지(1.5~5초)** 는 부트로더 실행 중에
벌어지는 일이라 펌웨어가 개입할 수 없다.

| | 재열거 실패 (주원인) | 업데이트 중 USB 정지 |
|---|---|---|
| 부트로더 V260824R1 (근본 해결) | O | O |
| 펌웨어 V260824R2 (본 보완책) | O | X |

**배포 전략**
- 이후 출고분: 부트로더 V260824R1 적용 (ST-LINK로 내부 플래시 기록)
- 기출하 보드: 부트로더를 UF2로 갱신할 수 없으므로(UF2는 외장 플래시의 FIRM/UPDATE
  영역만 기록) 본 펌웨어 보완책을 배포

## 5. 검증

**빌드** — H7S 5종 모두 통과, 경고 0건 (arm-none-eabi-gcc 10.3.1)

| 보드 | RAM | FLASH |
|---|---|---|
| may65 | 64,256 B | 117,700 B |
| intigrity80 | 64,288 B | 117,748 B |
| brick60 | 64,288 B | 117,748 B |
| brick65 | 64,312 B | 117,892 B |
| sculpturei | 64,200 B | 118,092 B |

FLASH 증가는 V260720R1 대비 **+8 B**다.

**실기 확인 항목**
1. 구(舊) 부트로더가 올라간 보드에서 UF2 업로드 → 자동 시작이 10회 연속 성공하는지.
2. 콜드부트(전원 인가) 시 열거 지연이 체감되지 않는지.
3. VIA 리셋, BootMode 변경(FS 1K / HS 2K / 4K / 8K) 후 재열거가 정상인지.
4. USB 허브 경유 및 다른 PC에서 동일한지.
